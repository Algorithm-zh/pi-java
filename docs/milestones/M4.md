# M4：Agent Loop 与只读 Web demo

> 日期：2026-10-22
> 状态：已完成
> 提交：`feat(agent): agent loop, sse and read-only web demo`

## 目标

把 M2 的流式 LLM 与 M3 的只读工具目录接成可运行的 Agent Loop，并提供无需 API Key
即可体验的 Web UI：

- 领域层能表达 run 快照、预算、终止原因与运行事件；
- 应用层完成“用户消息 → 模型流 → 工具批次 → 工具结果 → 下一轮 → RUN_SUMMARY”；
- 触发层提供会话/运行 REST 与 SSE，支持断线后按 `Last-Event-ID` 重放；
- demo profile 使用 H2 + Fake LLM，浏览器可新建会话、流式查看、停止与刷新恢复。

## 交付物

### 运行时领域 `domain.agent`

| 类型 | 说明 |
|---|---|
| `AgentRun` | 不可变状态快照：状态、预算、turns、toolCalls、usage、时间、终止原因 |
| `RunStatus` | `RUNNING / COMPLETED / FAILED / ABORTED` |
| `RunStopReason` | `STOP / LENGTH / MAX_STEPS / CANCELLED / TIMEOUT / ERROR` |
| `RunBudget` | 默认 20 轮、100 工具调用、15 分钟；硬上限 1 小时 |
| `RunEvent` / `RunEventType` | 顺序事件与稳定 wire name；data 只放 JSON 友好值 |
| `RunId` | ULID 包装 |

`AgentRun` 的每次变更返回新快照；终态不可迁移。run 不持久化，事实仍落在 entry 日志。

### 应用层 `application.agent`

```text
application.agent
├── command/SendMessageCommand, readmodel/RunHandle
└── service/
    ├── AgentLoopService        turn 推进、终止判定、统一收尾
    ├── RunRuntime              预留、追加、finish、取消、终态等待
    ├── ActiveRunRegistry       每会话唯一活跃 run、终态保留 200 条
    ├── RunDispatcher           全局并发许可（默认 4），满额立即拒绝
    ├── TurnPipeline            投影、请求、流式、工具批次装配
    ├── TurnExecutor            LLM 流读取、增量发布、取消保留部分文本
    ├── ToolCallCoordinator     预检、策略、并行/串行、成对结果
    ├── SessionEntryAppender    短事务追加 entry 与状态迁移
    ├── SystemPromptBuilder     身份、工作区、工具、只读约束
    ├── RunEventHub             每 run 500 条缓冲、30 分钟保留、重放
    └── RunEventPublisher       稳定事件数据形状
```

关键不变量：

- 一个会话同时只有一个活跃 run；
- 每个 toolCall 必须得到一条 toolResult，即使未注册、被拒绝、超预算或取消；
- 所有终止路径都写且只写一条 `RUN_SUMMARY`；
- LLM 与工具执行期间不持有数据库事务。

### HTTP 与 SSE

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/v1/sessions` | 创建会话 |
| `GET` | `/api/v1/sessions` | 列表（可选 `cwd`、`limit`） |
| `GET` | `/api/v1/sessions/{id}` | 详情 |
| `GET` | `/api/v1/sessions/{id}/entries` | 分支 entry envelope |
| `GET` | `/api/v1/sessions/{id}/run` | 活跃 run 或 204 |
| `POST` | `/api/v1/sessions/{id}/messages/stream` | 发起 run 并订阅 SSE |
| `POST` | `/api/v1/sessions/{id}/abort` | 取消，返回 202 |
| `GET` | `/api/v1/runs/{runId}` | run 快照 |
| `GET` | `/api/v1/runs/{runId}/events` | `Last-Event-ID` 回放 |
| `GET` | `/api/v1/system/info` | 版本、默认工作目录、OS |

SSE 事件为 `run.started / turn.started / message.started|delta|completed /
tool.started|completed / run.completed|failed`，`id=runId:seq`，心跳 15 秒。
事件缓冲淘汰起点时发送 `replay.gap`。

### Web UI

原生 HTML/CSS/JS，无构建步骤：

- 会话侧栏、新建会话对话框（标题、工作目录、模型档案）；
- 流式文本、工具卡片（参数、输出、错误态）、停止按钮、usage；
- 刷新页面后按 URL 中的 session 恢复历史；有活跃 run 时走重连接口；
- Fake 示例：`/read README.md`、`/ls .`、普通问候。

### Demo 装配

- `DemoDataInitializer` 幂等创建 `fake-demo` 模型（FakeProvider）；
- demo profile 默认启用 `pi.fake.demo-mode=true`，无需 API Key；
- 默认只监听 `127.0.0.1`，无鉴权。

## 关键设计决策

1. **Run 只存在于内存**：不建 run 表，避免进程崩溃后留下永远 RUNNING 的记录；
   对用户有意义的结果全部写入 append-only entry。
2. **快照而非可变聚合**：`AgentRun` 每次变更返回新 record，状态迁移集中在 `finish`，
   便于并发读取与测试断言。
3. **HTTP 立即返回 runId**：控制器同步完成预留与用户消息落库，run 在虚拟线程执行；
   SSE 响应体持续输出，终态后关闭。这样客户端无需长轮询。
4. **事件同步重放 + 再订阅**：`RunEventHub.subscribe` 在同一把锁内完成缓冲重放与监听器
   注册，避免“重放结束到实时开始”之间的缝隙。
5. **取消是协作式的**：取消标志在轮次开始、流增量、工具调用前检查；LLM 流被关闭，
   已输出文本保留，最终写 CANCELLED，不删除历史。
6. **M4 审批占位**：`ASK` 策略不执行工具，直接生成“需要审批，M6 提供”的错误结果；
   不引入半成品审批状态机。
7. **惰性自愈**：单实例下，发现数据库 RUNNING 但内存无活跃 run 时，下一次发消息前
   直接恢复 IDLE；不做启动全表扫描。

实际运行（Java 21，端口 18080，H2 内存库，demo profile）：

1. `/api/v1/system/info` 返回版本、`D:\code\pi-java` 与 Windows 11；
2. `/api/v1/models` 返回 `fake-demo`（FAKE，enabled）；

5. 刷新页面后历史消息、工具卡片、usage 与“已取消”状态均恢复。

## 已知限制

- 没有审批与写工具；`ASK` 一律拒绝执行，`write/edit/bash` 尚未提供；
- 没有上下文压缩、Skills、子代理与 CLI；
- 会话标题不做自动生成，默认“新会话”；
- SSE 发送为同步写，慢消费者会阻塞该 run 的广播；没有有界队列；
- 事件缓冲与活跃 run 都在进程内，重启后不能重放；依靠前端重新拉取 entry；
- 悬空会话自愈只适用于单实例；多实例需要持久化 run 租约；
- Fake demo 的流非常快，手动点击“停止”经常落在完成之后；取消行为由自动化测试
  与并发 abort 脚本验证。
