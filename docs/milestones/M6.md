# M6：审批与写工具

> 日期：2026-10-22
> 状态：已完成
> 提交：`feat(governance): approval workflow and write tools`

## 目标

把工具管线从“只读、默认放行”推进到“高风险操作可审计、可阻塞、可拒绝”：

- 审批是独立聚合与待办投影，决策终态同时写入会话日志；
- 工具策略按 `WORKSPACE > USER > 风险默认` 解析，`ASK` 阻塞等待人工决策；
- 增加 `write / edit / bash`，文件工具统一走路径沙箱；
- 审批、策略管理通过 HTTP 与 SSE 暴露，Web UI 提供审批弹窗；
- Fake demo 可用 `/write` 触发完整审批链路，无需 API Key。

## 交付物

### 领域层 `domain.governance`

| 类型 | 说明 |
|---|---|
| `ApprovalRequest` | 审批聚合根：PENDING → APPROVED / DENIED / EXPIRED / CANCELLED |
| `ApprovalId` / `ApprovalStatus` / `ApprovalDecision` | 标识、状态与用户决策 |
| `ApprovalContext` | 会话、run、工具调用、工具名与风险级别 |
| `ApprovalArguments` | canonical JSON、SHA-256 digest 与脱敏参数 |
| `ApprovalRepository` | 插入、按 ID/会话查询、`updateIfPending` CAS |
| `ApprovalArgumentsSanitizer` | 稳定序列化、敏感键脱敏、digest 计算 |
| `ToolPolicyRule` / `PolicyEffect` / `PolicyScope` | 已有的策略模型，M6 接入执行管线 |

不变量：终态不可回退；终态必须有决策者与决策时间；TTL 必须为正且不超过 24 小时；
PENDING 不允许携带决策信息。

### 应用层 `application.governance` 与工具管线

| 类型 | 说明 |
|---|---|
| `ApprovalApplicationService` | 创建待办、CAS 决策、APPROVAL entry 双写、afterCommit 发布 |
| `ApprovalGateService` | 为工具线程提供阻塞等待：批准、拒绝、取消、TTL 过期 |
| `ApprovalWaitRegistry` | `CompletableFuture` 等待句柄，事务提交后唤醒 |
| `ApprovalEventPublisher` | 发布 `approval.requested / resolved` SSE 事件 |
| `ToolPolicyApplicationService` | 策略查询与幂等 upsert（版本号递增） |
| `ToolCallPreflight` | 从协调器拆出的策略/预算预检，产出 `PreparedCall` |
| `ToolBatchContext` | 工具批次的不可变参数对象，避免超长参数列表 |
| `ToolCallCoordinator` | `ASK` 时打开审批、阻塞等待终态，批准后执行，否则写配对错误结果 |

事务边界：创建/决策各自是短事务，等待期间不持有数据库事务；事务提交后才发布 SSE
并唤醒等待线程。提交失败时等待者继续阻塞，由 gate 在 TTL 到期后重新读取状态。

### 基础设施

| 类型 | 说明 |
|---|---|
| `MyBatisApprovalRepository` / `ApprovalPO` / `ApprovalMapper` | V5 审批表读写与 CAS |
| `ApprovalArgumentsCodec` | 脱敏参数 JSON 的编解码 |
| `WriteToolHandler` | 新建/覆盖文件，自动创建父目录，拒绝目录目标与越界路径 |
| `EditToolHandler` | 唯一文本匹配替换，支持 `replaceAll`，拒绝二进制/大文件 |

| `BuiltInToolHandlers` | 内置工具执行体统一装配 |

### HTTP、SSE 与 Web UI

- `GET /api/v1/approvals?sessionId=&status=`、`GET /api/v1/approvals/{id}`；
- `POST /api/v1/approvals/{id}/decision`，`decision` 取 `APPROVE / DENY`，
  HTTP 决策者固定为 `local-user`；
- `GET/PUT /api/v1/tool-policies`；
- SSE `approval.requested`（脱敏参数，不含 digest）与 `approval.resolved`；
- 审批弹窗：队列去重、风险徽标、脱敏参数、digest 详情、倒计时、批准/拒绝、
  Esc 阻止误关、刷新后恢复待办；
- 错误映射：审批不存在 404，终态重复决策 409。

### 数据库

V5 `pi_approval_request`（H2 / MySQL 两份方言）：

- 唯一键 `(run_id, tool_call_id)` 防止同一调用重复开单；
- `args_digest` 与 `args_redacted_json` 分离，原始参数不落库；
- `(status, expires_at)` 索引供过期扫描；会话外键级联删除；
- 表是待办投影，不是审计事实源：终态必须同步追加 `APPROVAL` entry。

## 关键设计决策

1. **审批与会话日志双写**：数据库表用于查询待办与 CAS，审计以 append-only 的
   `APPROVAL` entry 为准。即使待办表被清理，会话日志仍能还原“谁在何时批准了什么”。
2. **等待不占事务**：工具线程在事务外阻塞于 `CompletableFuture`；审批服务只在
   创建和决策的瞬间开启事务。避免人工审批的分钟级等待长期占用连接池。
3. **终态写入用 CAS**：`updateIfPending` 保证批准、拒绝、取消、过期并发到达时只有
   一个成功；失败方得到 409，而不是覆盖别人的决策。
4. **digest 与展示参数分离**：digest 基于完整 canonical JSON 计算，用于校验参数
   未被篡改；HTTP 详情返回 digest 和脱敏参数，SSE 只返回脱敏参数，避免日志/事件流
   扩散完整命令或文件内容。
5. **过期惰性处理**：决策入口先检查 TTL，过期即落 EXPIRED 并返回冲突；等待方在
   TTL 到期后重新读取。没有引入后台调度器，启动时遗留 PENDING 的批量清理后移。
6. **拒绝也是配对结果**：拒绝、过期、取消都生成 `isError=true` 的 `tool.completed`，
   保留原 toolCallId，保证 toolCall/toolResult 配对不破坏会话日志。
7. **写工具串行**：`write/edit` 为 HIGH、`bash` 为 CRITICAL，均标记 SEQUENTIAL；
   只读工具保持并行。审批通过后仍由原协调器执行，不绕过沙箱、超时与结果回写。
8. **预检拆分为独立组件**：为满足文件/方法/参数上限，把策略解析、预算判断与
   `PreparedCall` 从 `ToolCallCoordinator` 拆到 `ToolCallPreflight`；
   `ToolBatchContext` 收敛批次参数，行为不变。

## 实际运行

Java 21，端口 8081，临时工作区，demo profile（H2 文件库 + Fake LLM）：

1. 新建会话，发送 `/write smoke-approved.txt hello-m6`；
2. SSE 出现 `approval.requested`，待办返回 `toolName=write`、`riskLevel=HIGH`、
   脱敏参数、64 位 `argumentsDigest`、`status=PENDING`；
3. `POST .../decision` 批准，返回 `status=APPROVED`、`decidedBy=local-user`；
4. 文件落盘，内容为 `hello-m6`；SSE 顺序为
   `run.started → tool.started → approval.requested → approval.resolved →
   tool.completed → turn.started → run.completed`；
5. 第二个 run 发送 `/write smoke-denied.txt nope`，拒绝后文件不存在，
   `tool.completed` 为 `isError=true`、`content=用户拒绝执行工具 write: smoke deny`，
   run 仍以 `run.completed` 结束。

Web UI 另做过浏览器走查：审批弹窗正确展示脱敏参数与倒计时；批准后文件写入；
拒绝后工具卡片为失败态；刷新页面后未决策的待办重新弹出，继续批准可完成写入。

## 已知限制

- `approvalMode=SESSION/ALWAYS` 的“记住批准”尚未执行，字段已持久化；
- 策略中的 `timeoutMs` 尚未覆盖工具默认超时；
- 启动时遗留 PENDING 审批不会批量置为 EXPIRED，只在决策或等待超时时收敛；
- 审批 UI 不渲染历史 `APPROVAL` entry，审计仍以会话日志/API 为准；
- `bash` 只能限制 cwd、审批、超时与输出，无法做路径级沙箱；
- 插件工具已走同一审批管线，但插件命令、hook、拦截器仍未实现。
