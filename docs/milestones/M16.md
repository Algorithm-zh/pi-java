# M16：图片与多模态输入

> 日期：2026-10-27
> 状态：已完成；隔离副本 `mvn -q verify` 全绿，8080 实例未受影响
> 范围：ImageBlock、附件存储与 API、视觉能力门禁、OpenAI-compatible 多模态映射、
> Web 图片选择/粘贴/拖放与历史渲染

## 目标

让用户能把截图直接贴进对话，而不是先描述界面再让模型猜：

- 图片只上传一次，会话历史里始终能看到原图；
- 模型不支持视觉时提前拦住，而不是发出去才失败；
- 图片不把数据库、SSE 事件和上下文预算撑爆；
- 不引入前端框架，保持现有原生 ES 模块结构。

## 交付范围

- 领域：
  - `ImageBlock(attachmentId, mediaType, name)` 加入 sealed `ContentBlock`；
  - `ModelCapabilities.vision`、`MODEL_CAPABILITY_MISSING`、
    `ATTACHMENT_NOT_FOUND`、`ATTACHMENT_INVALID`、`ATTACHMENT_STORE_FAILED`；
  - `SessionEntry.CURRENT_PAYLOAD_VERSION` 升到 2；`entry` 只存引用；
- 应用：
  - 附件端口 `AttachmentStore` 与 `AttachmentApplicationService`；
  - PNG/JPEG/WebP/GIF 文件头识别、单图 5 MB、每条消息 4 张、重复 ID 拒绝；
  - `SendMessageCommand.attachmentIds`；`UserMessage.create` 统一图文组装；
  - 首条消息只有图片时用「N 张图片」作为标题；
- 基础设施：
  - `FileSystemAttachmentStore`：`${PI_DATA_DIR}/attachments/<ulid>.bin` +
    `<ulid>.json`，先写二进制再写元数据；
  - OpenAI-compatible 请求把图片映射为 `image_url` base64 data URI；
    没有文本时不发空 `text` 元素；字节缺失时降级为文本占位；
  - Fake provider 与 demo 脚本识别图片并回显数量；`fake-demo` 档案升级为支持视觉；
- 入口：
  - `POST /api/v1/attachments`（multipart，字段名 `file`）、
    `GET /api/v1/attachments/{id}`；
  - OpenAPI 自动收录两个新端点与 `attachmentIds` 字段；
  - Web UI：附件按钮、文件选择、粘贴、拖放、上传中禁用发送、本地预览、
    历史图片与移动端布局；
  - `application.yml`：multipart 5 MB / 6 MB，`pi.attachments.dir`。

## 关键设计

- **引用与字节分离**：entry、SSE 事件、token 估算都只接触 `attachmentId`；
  图片字节留在数据目录，会话删除后也不会把数据库拖大。
- **门禁先于写历史**：`AgentLoopService` 在 `appendUserAndStart` 之前校验
  `capabilities.vision`，拒绝时不会留下用户消息或占用 run；前端用同一能力位
  提前禁用入口，两端提示一致。
- **格式按文件头判断**：不信任 `Content-Type` 与扩展名，`ImageFormats` 只认四种
  位图签名，SVG 等可携带脚本的格式直接拒绝。
- **上传先于发送**：消息只带已落库的附件 ID，避免“消息已写、图片还没到”的中间态；
  上传未完成时发送按钮禁用，流式生成中不接收新附件。
- **本地预览、服务端回读**：选择后立即用 blob URL 显示，上传完成换成
  `/api/v1/attachments/{id}`，刷新后仍从服务端加载。
- **能力位可演示**：demo 档案默认支持视觉，Fake 模型回显图片数量并说明
  “不会真正解析图片”，让离线环境也能验证完整链路。

### 本地运行

用隔离参数启动 0.2.0 jar（端口 18081，`PI_DATA_DIR` 指向临时目录，
工作目录为临时工作区），未触碰 8080 实例：

- `/api/v1/models` 返回 `fake-demo` 且 `capabilities.vision=true`；
- 新建会话、选择图片后预览立即出现，上传完成后 URL 变为
  `/api/v1/attachments/<ulid>`；
- 发送「这张图的主色调是什么」+ 1 张图，Fake 回复
  `我收到：这张图的主色调是什么（另附 1 张图片）`；
- 只发图片（不带文本）也能发送，回复 `我收到：1 张图片`；
- 刷新页面后两张图片仍正常渲染（320×200 与 200×120 原图）；
- 粘贴与拖放各上传一张；`notes.txt` 被拒绝并提示
  `仅支持 PNG、JPEG、WebP 或 GIF 图片`；6 MB 图片被拒绝并提示超过 5 MB；
- 移动端 390×844（CDP 设备模拟）无横向溢出，图片与正文都在视口内；
- 视觉门禁：
  - 新建 `vision=false` 的模型档案后打开会话，点击添加图片提示
    `当前模型未声明图片输入能力，请在设置里改用支持视觉的模型`；
  - 直接调用发送接口返回 400 `MODEL_CAPABILITY_MISSING`，会话保持 `IDLE`、
    entry 列表为空、`GET /run` 返回 204。

### 附件 API

```bash
curl -F "file=@docs/images/chat.png" http://127.0.0.1:18081/api/v1/attachments
```

- 返回 201 `{id,name,mediaType,size,url}`；
- `GET /api/v1/attachments/{id}` 返回 200、`Content-Type: image/png`、
  `Cache-Control: private, max-age=86400`、inline 文件名；
- 文本文件返回 400 `ATTACHMENT_INVALID`。

## 已知限制

- 附件没有回收、去重、配额与 EXIF 清理；删除会话不会删除图片文件；
- 只支持四种位图，没有 PDF、音频、视频，也没有缩放/压缩与缩略图；
- 图片以 base64 进入模型请求，大图会显著增加请求体与上下文成本；
- CLI 仍只支持文本输入，图片能力只在 Web 入口提供；
- v0.2 无鉴权，附件下载同样只应通过回环地址访问。
