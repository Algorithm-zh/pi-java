# M17：附件生命周期与图片压缩

> 日期：2026-10-27
> 状态：已完成；`mvn -q test` 828 个测试全绿，独立 18081 实例浏览器验收通过，8080 实例未受影响
> 范围：内容去重、总配额、EXIF 等元数据清理、孤儿回收与统计接口、
> 定时/手动清理、Web 上传前压缩与设置页存储卡片

## 目标

M16 让图片能进对话，但附件只会增加、不会减少：重复截图各占一份空间，相册照片的
EXIF 会连同拍摄地点一起落盘，删除会话后图片仍留在数据目录。M17 把附件当作需要
生命周期管理的资源：

- 相同内容只存一份，重复上传直接复用已有记录；
- 落盘前剥离 EXIF/XMP/时间等元数据，只保留像素数据；
- 用总配额兜住磁盘占用，超限时明确拒绝而不是写满磁盘；
- 无人引用的图片在宽限期后自动回收，设置页能看到用量并手动触发；
- 大图在浏览器里先缩到 1568 px、转 WebP，减少上传时间与请求体。

## 交付范围

- 领域：
  - `ATTACHMENT_QUOTA_EXCEEDED`；HTTP 映射为 `413 Payload Too Large`；
- 应用：
  - `AttachmentStore` 增加 `findByDigest`、`list`、`totalBytes`、`delete` 与
    `StoredAttachment(metadata, createdAt)`；
  - 新端口 `ImageSanitizer`、`AttachmentReferenceSource`；
  - `AttachmentApplicationService`：SHA-256 去重、清洗后再计量、512 MB 默认配额、
    `stats()`；
  - `AttachmentMaintenanceService`：只删除“无引用且超过宽限期”的附件；
  - `AttachmentStats`、`AttachmentReclaimResult`；
- 基础设施：
  - `FileSystemAttachmentStore`：摘要索引（懒加载 + 同步）、去重写入、列表、总量、
    删除；元数据读写拆到 `AttachmentMetadataFile`；
  - `ImageMetadataStripper`：纯 Java 解析 JPEG/PNG/WebP/GIF，移除元数据段；
  - `SessionEntryAttachmentReferenceSource`：扫描全部 `pi_session_entry.payload_json`
    的 `attachmentId`；
  - `AttachmentGcJob`：每日 `@Scheduled` 回收；
- 入口：
  - `GET /api/v1/attachments/stats`、`POST /api/v1/attachments/gc`；
  - 设置 → 系统信息新增“附件存储”卡片：数量、占用、配额与清理按钮；
  - Web 上传前压缩：最长边 1568 px、WebP 0.85；只对超过 1.5 MB 的非 GIF 图片生效；
- 配置：
  - `pi.attachments.max-total-bytes`（默认 512 MB，0 表示不限制）；
  - `pi.attachments.gc-min-age`（默认 `1h`）；
  - `pi.attachments.gc-cron`（默认每日 `0 40 3 * * *`）。

## 关键设计

- **摘要基于清洗后的字节**：先剥离元数据再算 SHA-256。同一张图带不同 EXIF 也会
  命中同一条记录，索引与磁盘内容始终一致；重复上传返回首次写入的文件名。
- **先清洗再计量配额**：配额按实际落盘字节计算，避免“原图很大、清洗后很小”被误拒；
  去重在配额检查之前，重复内容不会因为“看起来要再占一份”而失败。
- **引用扫描覆盖全部历史**：不只看当前分支或未删除会话，而是扫描所有 entry 的
  payload；正则只匹配 `"attachmentId":"..."`，对未知 payload 字段保持宽容。
- **宽限期保护上传中图片**：刚上传、还没随消息发送的附件不会立刻被删；默认 1 小时，
  可配置为 `0s` 用于演示或测试。删除是逐条独立操作，失败不会中断整轮回收。
- **元数据清理只动元数据**：JPEG 丢弃 APP1/APP13/COM，PNG 丢弃 eXIf/tEXt/zTXt/iTXt/tIME，
  WebP 丢弃 EXIF/XMP 并修正 VP8X 标志与 RIFF 长度，GIF 只丢注释扩展；像素数据
  原样复制。解析失败时返回原字节，不因清理器 bug 让上传失败。
- **压缩在浏览器完成**：用 `createImageBitmap(..., {imageOrientation: "from-image"})`
  尊重手机照片方向，画到 1568 px 画布后 `toBlob("image/webp", 0.85)`；GIF 跳过以
  保留动画，压缩失败或浏览器不支持时回退原图。服务端仍按 5 MB 重新校验，
  不把前端压缩当作安全边界。
- **UI 如实展示**：附件卡片显示压缩后大小，悬停提示“原图 X，已压缩为 Y”；
  设置页的清理按钮与定时任务走同一个应用服务，结果用 toast 反馈。

### 接口抽查

```bash
curl http://127.0.0.1:18081/api/v1/attachments/stats
curl -X POST http://127.0.0.1:18081/api/v1/attachments/gc
```

- `stats` 返回 `{count, bytes, quotaBytes}`；
- `gc` 返回 `{scanned, deleted, freedBytes}`；无引用且超过宽限期的附件才计数；
- 配额设为 1 MB 后再次上传大图返回 413 `ATTACHMENT_QUOTA_EXCEEDED`
  （由控制器单元测试覆盖）。

## 已知限制

- 引用扫描依赖 payload 中的字段名与 JSON 形状；未来若 payload 改存附件列表的
  嵌套结构，需要同步调整正则或改为类型化解析；
- 回收任务运行在单实例内，没有跨进程锁；多实例部署前需要租约或外部任务调度；
- 摘要索引首次使用会读取全部 `.json` 元数据，附件很多时首轮启动略慢；
- GIF 不做压缩，只清理注释扩展；动画帧与体积保持原样；
- 压缩只在 Web 入口生效，CLI 仍只支持文本；
- 元数据清理是尽力而为：格式解析失败时保留原字节，不阻断上传；
- 配额是全局总量，没有按会话或用户拆分；无鉴权时任何本地调用都能触发回收。
