# M8：同步子智能体

> 日期：2026-10-22
> 状态：已完成
> 提交：`feat(subagent): synchronous subagents with depth and toolset limits`

## 目标

让主代理可以把一个**自包含**的子任务交给子代理执行，并只拿回结论：

- 子代理是新会话，挂在会话树的父节点下，可追溯、可审查；
- 工具与权限**只能收紧**：工具子集 = 父快照 ∩ 白名单，达到深度上限后连
  `subagent` 工具本身都会从目录里消失；
- 失败、超时、取消都不打断父循环——父模型永远拿到一条结构化的 toolResult；
- 同步执行，语义最简单：像调用普通工具一样拿到结论。

## 交付物

### 领域层 `domain.subagent`

| 类型 | 说明 |
|---|---|
| `SubagentMode` | `SPAWN`（零父上下文）/ `FORK`（复制父投影） |
| `SubagentPolicy` | 最大深度、默认超时、超时上限；`allowsChildOf(depth)` 判断还能否派生 |
| `SubagentRequest` | 任务、角色、工具白名单、超时；构造时完成规范化与校验 |
| `SubagentResult` | 子会话、终止原因、摘要、用量、轮数、耗时；`isError()` 与 `render()` |
| `SubagentToolset` | 计算工具子集：交集 + 深度裁剪（纯函数） |

不变量：

| 编号 | 不变量 | 执行位置 |
|---|---|---|
| INV-16 | 子代理工具集 ⊆ 父工具集 | `SubagentToolset.derive` |
| INV-17 | 深度达到 `maxDepth` 时子工具集不含 `subagent` | `SubagentToolset` + 目录 |
| INV-18 | 超时不超过工具调度上限（600 秒），超出直接拒绝而非静默截断 | `SubagentPolicy` |
| INV-19 | 子代理失败/超时/取消必须以 toolResult 回写，不得抛出到父循环 | `SubagentToolInvoker` |

### 应用层 `application.subagent`

| 类型 | 说明 |
|---|---|
| `SubagentSessionFactory` | 由父会话构造子会话：沿用模型与沙箱、`origin=SUBAGENT`、深度 +1 |
| `SubagentExecutionService` | 持久化子会话、启动子 run、有界等待、聚合最后一条助手文本 |
| `SubagentService` | 用例编排：深度校验 → 工具子集 → 创建 → 组装提示 → 执行 |
| `SubagentToolInvoker` | `@Primary` 的 `ToolInvoker`：截获 `subagent`，其余转发给真实执行器 |
| `SubagentRegistry` | `subagent` 工具定义（schema、风险、超时） |

### 关键机制

**1. 循环依赖的处理**

子代理在工具管线内部启动 Agent Loop，形成结构性环：

```text
AgentLoopService → TurnPipeline → ToolCallCoordinator → SubagentToolInvoker
   → SubagentExecutionService → AgentLoopService
```

在 `SubagentExecutionService` 中用 Spring `ObjectProvider<AgentLoopService>` **延迟解析**，
只在真正执行子代理时才取用。相比全局 `spring.main.allow-circular-references=true`，
这里只放开了一处必然存在的环，其余循环依赖仍会被容器拒绝。

**2. 为什么 `subagent` 不在 `BuiltInToolCatalog` 里**

内置工具与它的执行体都在基础设施层，而子代理需要应用层编排（创建会话、启动 run）。
若把定义放进内置目录，基础设施就得反向依赖应用层——违反分层。因此：

- 定义放在应用层 `SubagentRegistry`；
- `ToolConfiguration` 把它与内置工具合并后交给 `RuntimeToolRegistry`；
- 执行由 `SubagentToolInvoker` 截获，`RuntimeToolInvoker` 保持单一职责。

**3. 工具调用携带会话上下文**

`ToolInvocation` 新增可空字段 `originSessionId`。只有需要“知道自己是谁的调用”的工具
（目前是 `subagent`）会读取它；其余工具与既有测试不受影响（保留四参数构造器）。

**4. 子代理的输出契约**

子代理的首条用户消息包含：角色（可选）、任务、可用工具清单、输出要求。
明确“只输出结论、带证据、失败要说明卡点”，避免子代理把冗长的过程回传给父模型。

## 配置

```yaml
pi:
  agent:
    max-subagent-depth: 2              # 用户 → 子 → 孙
    subagent-timeout-seconds: 300      # 默认超时
    subagent-max-timeout-seconds: 600  # 上限，不得超过工具调度上限
```

## 实际运行

启动后 `GET /api/v1/tools` 返回：

```text
bash:DENY, edit:ASK, glob:ALLOW, grep:ALLOW, ls:ALLOW, read:ALLOW, subagent:ASK, write:ASK
```

`subagent` 默认 `ASK`：派生子代理会消耗额度，与写操作一样需要人工确认。
放行后模型即可在对话中自行调用。

## 已知限制

- **同步阻塞**：父 run 的工具线程会一直等到子 run 结束或超时；由于每会话只允许一个活跃 run，
  子代理期间父会话不能并行处理其他消息；
- **超时上限 600 秒**：受工具调度器 `Future.cancel(true)` 的约束，无法配置更长；
- **沙箱未进一步收紧**：子会话直接沿用父会话的 `SessionConfig`，满足“不放宽”，
  但没有实现“限制到子目录”这类更强收紧；
- **审批未做会话级继承**：子代理内部的写操作仍各自弹审批，没有“本会话已允许”的复用；
- **Fake demo 模型无法驱动子代理**：它按最后一条用户消息匹配指令，而子代理提示词带前缀，
  因此 demo 下只能验证链路，真实效果需要真实模型；
- **无 SSE 子会话事件**：暂不向前端推送 `subagent.*`，子会话通过会话树 API 查看；
- **UI 未展示会话树**：目前只能通过 `GET /sessions/{id}` 与仓储查询子会话。
