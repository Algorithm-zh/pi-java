# ADR 0002：v0.1 不引入 Redis，只使用本地 Caffeine

- 状态：Accepted
- 日期：2026-10-21
- 决策者：pi-java 架构

## 背景

Agent 运行需要缓存一些读多写少的数据（模型档案、工具策略、Skill 目录），
但会话日志必须强一致；SSE 连接、审批等待者、活跃 run 都在进程内。

引入 Redis 会带来：

- 额外的部署与运维成本；
- 缓存与数据库一致性问题；
- 分布式锁、事件总线、序列化协议等新的失败模式；
- v0.1 单机演示不需要的复杂度。

而如果不缓存，每次 run 都查模型与策略表，在本地开发与单机部署下也不构成瓶颈。

## 决策

v0.1 采用**有限本地缓存**，不引入 Redis：

| 数据 | 方案 | TTL / 失效 |
|---|---|---|
| ModelProfile | Caffeine `maximumSize=200` | 10 分钟；保存/停用后主动失效 |
| ToolPolicy | Caffeine `maximumSize=500` | 2 分钟；更新后按 workspace 失效 |
| SkillCatalog | Caffeine `maximumSize=100` | 5 分钟 + 目录 mtime 校验 |
| Plugin 工具快照 | `AtomicReference<PluginSnapshot>` | 每次 run 固定引用，卸载不影响运行中 run |
| 会话 / entry / 投影 | **不缓存** | 每次从 entry 重建，避免分支脏读 |
| 审批状态 / 工具结果 / LLM 响应 | **不缓存** | 实时读库或内存 |

部署明确为**单实例**：

- 同一 session 同一时刻只有一个活跃 run，由进程内 `RunRegistry` 保证；
- 追加 entry 的串行化由进程内会话锁 + 数据库唯一键/CAS 双保险；
- SSE emitter、审批等待者、事件重放缓冲都在进程内；
- 应用重启后，未完成 run 由恢复流程补写摘要，不依赖外部事件总线。

## 结果

正面：

- 少一个中间件，启动简单，demo 开箱即用；
- 会话一致性不依赖缓存失效策略；
- 缓存只影响配置类读模型，最坏情况是短暂使用旧策略，不会破坏日志。

负面：

- 不支持多实例横向扩展：SSE 与审批等待无法跨进程路由；
- 重启会丢失事件重放缓冲与活跃 run；
- 策略/模型更新在多实例下无法即时广播（v0.1 本来也不支持多实例）。

## 演进路径

未来需要多实例时，**不改领域层**，在应用层端口后增加实现：

- `CachePort`：Caffeine → Redis；
- `EventBusPort`：进程内事件 → Redis Pub/Sub 或消息队列；
- `RunRegistry` / 会话锁：本地 → 带租约的分布式协调；
- SSE 重放缓冲：进程内 → 共享存储。

这些都属于 v0.2+，且必须先有真实多实例需求，不能提前抽象。

## 替代方案

### 全部使用 Redis 缓存

对 v0.1 是过度设计；会话日志仍不能缓存，收益主要在配置读取，成本不匹配。

### 完全不缓存

实现更简单，但每次 turn 都查模型/策略，且 Skill 目录扫描会拖慢系统提示组装；
Caffeine 是零外部依赖的折中。

### 使用数据库做分布式锁

在单机场景没有收益；数据库锁还会把 LLM/工具等待时间带入事务，风险更高。
